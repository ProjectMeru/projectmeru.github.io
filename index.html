A modular ERP
framework in Go.

Every business function — contacts, products, CRM, sales, invoicing — is an addon: a folder with a manifest, some Go models and some XML. The kernel discovers it, resolves its dependencies, creates its tables and wires its menus. Postgres underneath, server-rendered HTML on top, no front-end build step anywhere.

Project Meru is the initiative. Sumeru is the framework it builds — that is the name you will see in the code, the CLI and the repository.

Heads up. Sumeru is pre-alpha. The framework runs and the lead-to-cash flow works end to end, but there is no release, no upgrade guarantee, and no test suite in the addon repos. Do not run your business on it yet.

The idea

Business software should be boring to operate.

An ERP touches money, stock and payroll, so it has to be dependable for a decade. Most of the effort in running one goes not to the business logic but to the machinery around it — the runtime, the workers, the broker, the upgrade window. Sumeru is an attempt to spend that effort somewhere better.

01

Deployment should be a copy

If getting to a running system takes an afternoon and a wiki page, upgrades will be rare and scary. Go compiles to one binary; the only thing beside it is Postgres.

02

Customisation should not fork

Every business changes something. If that change means patching core, the next upgrade is expensive — so the install ages in place instead.

03

Your data should stay yours

The schema is the part that outlives the software. It should be plain Postgres tables that any analyst or DBA can query without learning a framework first.

How Sumeru answers that

Three tiers, cleanly separated

The core framework, the standard business addons and your own workspace are three separate Go modules linked by replace directives. Your customisations live in your own module — you never edit core to add behaviour.

Addons integrate through events

No addon imports another addon. Invoicing reacts to a confirmed sales order it has no compile-time knowledge of, guarded by a registry lookup, so the same binary works whether or not Sales is installed.

Tables you can read

A model is a Go struct describing fields; the kernel turns it into a real Postgres table with real columns and indexes. Point any BI tool at it and the schema makes sense.

Conventions checked at startup

Folder name, manifest name, package name, blank imports, XML root elements and declared data files are all validated when the server boots. A malformed addon fails loudly rather than half-installing.

Capabilities

What the kernel gives every addon

An addon author writes business logic. Everything below is provided by the core, so it works the same way in invoicing as it does in an addon you wrote last week.

⬡

Model registry

Models register themselves from init(). The kernel keeps a name-to-model registry — account.move, crm.lead — that addons look each other up through at runtime.

↻

Schema sync

Tables and columns are derived from your field definitions and created on boot. Missing columns are added, indexes ensured. It is additive: nothing is dropped behind your back.

▤

Manifest & discovery

A manifest.json declares name, version, dependencies and data files. The kernel scans every configured addons path and topologically orders what it finds.

◈

XML views, menus, actions

Tree, form and kanban views, window actions and the menu tree are declared in XML and loaded into the database on install — no template compilation.

⚿

Groups, ACLs, record rules

Groups with inheritance, per-model access rights from CSV, and row-level record rules whose domains understand $uid and the active company.

⇄

Event bus

The ORM publishes record.created and record.updated; the scheduler publishes cron.tick. Addons subscribe without importing each other.

◉

JSON-RPC API

POST /api/rpc with an API key exposes search, search_read, read, create, write and unlink against any model you have rights to.

▦

Server-rendered UI

Go templates plus a render package that builds form, tree and kanban HTML. Plain CSS and native ES modules — no bundler, no minifier, no build step.

⌸

Multi-company

Companies, per-user company access and a switcher in the top bar. One database serves the whole group, with rules scoping records to the active company.

⧗

Scheduler

A minute-tick scheduler runs due sys.cron rows and publishes their events, so recurring work needs no external broker.

◎

Logging & audit

Structured JSON logs with optional size-based rotation, an in-app log viewer, and an audit trail recording writes and access denials.

⚑

Scaffolding

One command generates a complete addon — manifest, init, models, views, menus, security — already satisfying every startup convention.

Nothing imports sideways

No addon imports another addon's Go package. Invoicing subscribes to record.updated, checks whether sale.order is in the registry at all, and only then builds an invoice. Uninstall Sales and Invoicing keeps working.

Dependencies are declared, not imported

The depends array in the manifest drives install order and nothing else: sale needs product, contacts and crm installed, but never links against them.

// sumeru_addons/account/models/account_journal.go
//
// A model is metadata: a name and a list of fields. The kernel turns
// this into the account_journal table and registers it for lookup.

package models

import "sumeru/core/sdk"

type AccountJournal struct {
    sdk.BaseModel
}

func (AccountJournal) ModelName() string { return "account.journal" }

func (AccountJournal) Fields() []sdk.FieldDefinition {
    return []sdk.FieldDefinition{
        {Name: "name", Type: sdk.Char, String: "Journal Name", Required: true},
        {Name: "code", Type: sdk.Char, String: "Short Code", Required: true},
        {Name: "type", Type: sdk.Selection, String: "Type", Selection: [][]string{
            {"sale", "Sales"},
            {"purchase", "Purchase"},
            {"general", "Miscellaneous"},
            {"bank", "Bank"},
            {"cash", "Cash"},
        }, DefaultVal: "general"},
        {Name: "default_account_id", Type: sdk.Many2One,
            Relation: "account.account", String: "Default Account"},
        {Name: "active", Type: sdk.Boolean, String: "Active", DefaultVal: true},
    }
}

func init() {
    sdk.RegisterModel(sdk.RegisterModelInput{Model: &AccountJournal{}, Module: "account"})
}

// sumeru_addons/account/init.go
//
// Invoicing has no compile-time knowledge of Sales. It listens for any
// record update, filters for sale.order, and checks the registry first —
// so this addon installs and runs with or without Sales present.

package account

import (
    "context"
    "log"

    "sumeru/core/event"
    "sumeru/core/orm"

    _ "sumeru_addons/account/models"
)

func init() {
    log.Println("Account Addon Loaded")
    event.Subscribe("record.updated", onSaleOrderToInvoice)
    event.Subscribe("record.updated", onPurchaseOrderToBill)
    event.Subscribe("record.updated", onMovePost)
}

func onSaleOrderToInvoice(ctx context.Context, ev event.Event) error {
    model, _ := ev.Payload["model"].(string)
    if model != "sale.order" {
        return nil
    }
    id, ok := coerceID(ev.Payload["id"])
    if !ok {
        return nil
    }
    if _, ok := orm.Registry["sale.order"]; !ok {
        return nil        // Sales is not installed — nothing to do.
    }
    // … confirm state, then create the draft invoice (idempotent).
}

Getting started

Two ways in

The same system, read from two directions: the commands that get it running, and the business flow it gives you once it is. Pick the tab that matches your job.

You need Go 1.26+ and PostgreSQL. Nothing else — no Node, no Docker, no message broker. Every command below runs from your workspace module, sumeru_custom_addons.

  1. 1

    Create the database and the config

    $ psql -U postgres -c "CREATE DATABASE sumeru;"

$ cd sumeru_custom_addons
$ cp sumeru.conf.example sumeru.conf
# edit db_host / db_user / db_password / db_name / http_port

    Paths inside the INI resolve against the file itself, not your shell. The addons_path key is what decides which addons exist at all.

  2. 2

    Point the workspace at the other two modules

    $ make replace-sumeru        SUMERU_ROOT=../sumeru
$ make replace-sumeru-addons ADDONS_ROOT=../sumeru_addons
$ make generate

    make generate rewrites addonimports/zimports.go, the blank imports that link every discovered addon into the binary. Run it whenever you add an addon.

  3. 3

    First boot — the setup wizard

    $ make run

Database is not initialized. Starting in SETUP MODE.
Visit http://localhost:9090/setup to initialize the system.

    There is no default admin account. The wizard at /setup creates your company and the first user; the email you give it becomes the login. The server restarts itself when it finishes.

  4. 4

    Install the business addons

    $ go run . -- -c sumeru.conf \
    -i contacts,product,crm,sale,sale_crm,account,purchase,hr \
    --stop-after-init

    Install order matters and follows depends. -i all is rejected on purpose — you name what you want. You can also install from the Apps screen once you are logged in.

  5. 5

    Run it

    $ make run
Server starting on :9090...

# open http://localhost:9090/  →  /web/home

The inner loop for a new addon

# scaffold — manifest, init.go, models, views, menus, security
$ go run ../sumeru/cmd/sumeru-bp -name my_module -out ./addons

# link it into the binary, then install it once
$ make generate
$ go run . -- -c sumeru.conf -i my_module --stop-after-init

# after editing any XML or the manifest's data list, reload it
$ go run . -- -c sumeru.conf -u my_module --stop-after-init
$ make run

Go code changes need a rebuild — that is what make run does. XML changes need -u, because views, menus and access rules live in the database once installed.

No commands here. This is what the system does once it is running, what you can change yourself, and what still needs an engineer.

01

You switch apps on

The Apps screen lists every available module — Contacts, Products, CRM, Sales, Invoicing, Purchase, Employees. Installing one brings its own menus, screens and permission groups with it. Install only what you use; the rest stays invisible.

02

Roles decide what people see

Users belong to groups, and groups carry both menu visibility and record access. A salesperson sees their own orders; a sales manager sees all of them. That rule is data, not code — it ships with the app and can be adjusted.

03

One database, several companies

A group of companies runs on a single system with a switcher in the top bar. Users are granted access to the companies they belong to, and records follow the company they were created in.

The flow that works today

Each arrow is automatic. The system reacts to a status change rather than asking someone to re-key the same figures into the next screen — and it will not create a duplicate if the same step fires twice.

  1. LeadCRM pipeline
  2. Wonstage marked won
  3. Quotationdraft sales order
  4. Sales orderconfirmed
  5. Invoicedraft, then posted
  6. Journal entriesbalanced, double-entry

Purchasing runs the same way: confirm a purchase order and a vendor bill is drafted against it. Posting a bill or an invoice writes the balanced journal lines behind it.

Who changes what

You, from the interface

Companies and users. Groups and who is in them. Chart of accounts and journals. CRM stages and lost reasons. Product categories and prices. Which apps are installed. Menus, once an app is on.

An engineer, in an addon

New fields on an existing screen. A new model or screen entirely. New automation between apps. Changes to how a document is numbered or validated. Anything that alters the shape of the data.

What is genuinely missing

Being honest about the gaps is more useful than a feature list:

  • Taxes — no tax engine on any document.
  • Payments — invoices carry a payment status, but nothing registers a payment or reconciles a bank statement.
  • Order totals — sales order amounts are stored, not yet computed from their lines.
  • Inventory — no stock, warehouses or manufacturing at all.
  • Reports — no printable documents, no financial statements.
  • Tests — the business addons have no automated test suite.

The catalogue

Addons that exist today

Four ship inside the core, eight in the standard addons module. Everything here is real code you can read — which is not the same as being finished.

base

Working

Partners, users, companies, groups, languages, API keys, sequences, attachments and the system metadata every other addon builds on.

mail

Working

Messages and the activity log behind the chatter panel. A platform module — it cannot be uninstalled.

automation

Partial

Scheduled jobs, server actions and workflow transitions. Cron rows fire; server-action execution is not implemented yet.

sumeru_ai

Placeholder

A demonstration of the UI extension points — a shell hook and a notebook hook. No model, no language model, no API calls.

contacts

Working

Customer and vendor directory. Adds no models of its own — it packages views, menus and access rights over the partner model in base.

product

Working

Products and product categories with sale and cost prices. Deliberately simple: no variants, no units of measure, no taxes.

crm

Working

Leads and opportunities, teams, pipeline stages, lost reasons. The richest data model in the set, with per-salesperson record rules.

sale

Partial

Quotations and sales orders with lines. Confirming an order flags it for invoicing. Amounts are not yet computed from the lines.

sale_crm

Working

The bridge: when a lead reaches a won stage, it becomes an opportunity and a draft quotation appears against it. Ninety lines, no models.

account

Working

Chart of accounts, journals, invoices, bills. Posting generates balanced double-entry journal items. The most complete addon in the set.

purchase

Partial

Requests for quotation and purchase orders. Confirming one drafts a vendor bill on the invoicing side. No receipts — there is no inventory yet.

hr

Partial

Employees, departments and job positions. A directory today: no contracts, attendance, leave or payroll.

No addons in this category yet.

What we committed to

The decisions behind Sumeru

These are the calls made early, written down so they can be held against us later. Each one closes off an alternative on purpose.

Decision What Sumeru does What that costs
Layout Three Go modules — core, standard addons, your workspace Three replace directives to keep pointed at the right paths
Linking Addons are compiled in via generated blank imports Adding one means regenerating and rebuilding — no runtime plugins
Database PostgreSQL only, with plain readable tables No portability to another engine
Schema Derived from field definitions, synced additively at boot No down-migrations; columns and tables are never dropped for you
Coupling Addons integrate through events and registry lookups Cross-addon flows are eventually consistent, and failures are quiet by design
UI Server-rendered HTML, plain CSS, native ES modules Less interactivity than a single-page app, and no component ecosystem
Isolation One database with multiple companies inside it Not multi-tenant — separate customers need separate deployments
Conventions Folder, package, manifest and XML shape validated at startup The framework fails fast and gives you less freedom in how you lay code out
Licence Dual: an Apache 2.0 community edition, plus a commercial enterprise edition Some addons will not be open source, and we have to say plainly which

The right-hand column is the honest half. If any of those costs is unacceptable for your business, Sumeru is the wrong tool and no amount of roadmap will change that.

Licensing

Where this is going

Roadmap

Four phases. Each one has to be genuinely usable before the next one starts — no phase exists only to prepare for a later phase.

  1. Phase 1 — Foundation

    Mostly done

    The kernel and the addon contract. This is the part you can read and rely on today.

    • Model registry, schema sync and the data layer
    • Addon discovery, convention checks, dependency ordering, install and update
    • Groups, access rights and record rules, enforced in the ORM
    • XML view engine, menus, actions and the rendered shell
    • Event bus, scheduler, structured logging and audit

  2. Phase 2 — Core business

    In progress

    The addons that make it an ERP rather than a framework. Lead to cash runs end to end; the money still needs work.

    • Done: contacts, products, CRM, sales, invoicing, purchasing, employees
    • Next: computed totals on orders and invoices, per-line invoicing
    • Next: a tax engine, then payments and reconciliation
    • Next: a test suite covering the commercial flow

  3. Phase 3 — Extended

    Planned

    The functions that surround the core — each one a test of whether the addon contract is good enough for authors outside the project.

    • Inventory: warehouses, stock moves, valuation
    • Manufacturing: bills of materials and work orders
    • HR beyond a directory: contracts, attendance, leave
    • Localisation packs, and translations wired through the UI

  4. Phase 4 — Platform

    Later

    Turning Sumeru from a system you deploy into one other people build on.

    • Studio: models and views defined without writing Go
    • Reporting: query builder, printable documents, statements
    • A distribution story for third-party addons
    • Isolation beyond multi-company, if the demand is real
