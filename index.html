The ERP that ships
as one binary.

Project Meru is a modular ERP written in Go. Every business function — accounting, inventory, sales, whatever you write yourself — is a module attached to a small, stable kernel. Compile the ones you need, copy one file to a server, run it.

Heads up. Meru is an in-progress project. The kernel and the module contract are being designed in the open — nothing on this page is production-ready yet.

The idea

Business software should be boring to operate.

An ERP touches money, stock and payroll, so it has to be dependable for a decade. Most of the effort in running one goes not to the business logic but to the machinery around it — the runtime, the workers, the broker, the upgrade window. Meru is an attempt to spend that effort somewhere better.

01

Deployment should be a copy

If getting to a running system takes an afternoon and a wiki page, upgrades will be rare and scary. One artefact, one command, no interpreter to install.

02

Customisation should not fork

Every business changes something. If that change means patching core, the next upgrade is expensive — so the install ages in place instead.

03

Your data should stay yours

The schema is the part that outlives the software. It should be readable SQL that any analyst or DBA can query without learning a framework first.

How Meru answers that

Compile it, ship it

Meru builds to a single binary with the modules you selected already inside it. Copy it to a server and run it. No interpreter, no virtual environment, no supervisor tree to keep alive.

Extend without forking

Modules attach to the kernel through a stable Go interface and a published event bus. You change behaviour by adding a module, never by editing core.

Postgres you can read

Real tables, real foreign keys, migrations written in SQL and checked into the repository. Point any BI tool at it and the schema makes sense on its own.

Tenancy in the kernel

Multi-tenant isolation is decided once, at the core, rather than being re-implemented — and occasionally forgotten — by every module.

Capabilities

What the platform gives every module

A module author writes business logic. Everything below is provided by the kernel, so it works the same way in accounting as it does in a module you wrote last week.

⬡

Module registry

Install, upgrade, disable and uninstall modules at runtime. The registry resolves dependency order before anything serves traffic.

⚿

Identity & RBAC

Users, groups, roles and record-level rules. Permissions are declared by the module and enforced by the kernel on every request.

▦

Typed data layer

Go structs map to Postgres tables with generated queries. Drop to raw SQL whenever the generated query is not the one you want.

↻

Migrations

Versioned, reversible, per module. Installing a module runs its migrations; removing it rolls them back cleanly.

⇄

Event bus

Modules publish domain events and subscribe to each other's without a compile time dependency. Inventory reacts to a sale it has never heard of.

⧗

Background jobs

A durable queue backed by Postgres. Retries, backoff and scheduled jobs, with no extra broker to operate.

◈

REST & gRPC

Both APIs are generated from the same model definitions, so the contract can never drift between them.

▤

Server-rendered UI

Go templates with progressive enhancement. There is no mandatory front-end build, and pages work before JavaScript arrives.

◉

Audit trail

Who changed what, when, and from where — recorded by the data layer rather than remembered by each developer.

⌸

Multi-tenancy

Schema-per-tenant isolation with a shared binary. One process can serve many organisations without sharing a row.

⚑

Localisation

Currencies, tax rules, date formats and translations are module-level data, so a country pack is just another module.

◎

Observability

Structured logs, Prometheus metrics and OpenTelemetry traces are on by default, labelled per module and per tenant.

// Every Meru module satisfies exactly this interface.
// If it does, the kernel can install, upgrade and remove it.

type Module interface {
    Name() string                 // "inventory"
    Version() string              // "0.4.1"
    Requires() []string           // {"identity", "accounting"}

    Models() []meru.Model         // tables, indexes, constraints
    Permissions() []meru.Perm     // declared, enforced by kernel
    Routes(r meru.Router)         // HTTP + gRPC endpoints
    Menu() []meru.MenuItem        // where it appears in the UI

    OnInstall(ctx context.Context, tx meru.Tx) error
    OnUpgrade(ctx context.Context, tx meru.Tx, from string) error
}
// Models are plain structs. Tags describe the column,
// and the kernel generates the migration and the queries.

type StockMove struct {
    meru.Base                     // id, tenant, created/updated, audit

    Product   meru.Ref[Product]   `meru:"required,index"`
    From      meru.Ref[Location]  `meru:"required"`
    To        meru.Ref[Location]  `meru:"required"`
    Quantity  meru.Decimal        `meru:"precision=16,scale=4"`
    State     MoveState           `meru:"enum,default=draft"`
}

func (m *StockMove) Validate() error {
    if m.Quantity.LessOrEqual(meru.Zero) {
        return meru.Invalid("quantity", "must be positive")
    }
    return nil
}
// Modules talk through events, never through imports.
// Inventory has no compile-time knowledge of Sales.

func (m *InventoryModule) OnInstall(ctx context.Context, tx meru.Tx) error {
    meru.Subscribe(ctx, "sales.order.confirmed", m.reserveStock)
    return nil
}

func (m *InventoryModule) reserveStock(ctx context.Context, e meru.Event) error {
    var order sales.ConfirmedOrder
    if err := e.Decode(&order); err != nil {
        return err
    }
    return m.reserve(ctx, order.Lines)   // runs in the job queue, with retries
}

What we committed to

The decisions behind Meru

These are the calls made early, written down so they can be held against us later. Each one closes off an alternative on purpose.

Decision What Meru does What that costs
Distribution A single static binary with modules compiled in Adding your own module means a rebuild
Database PostgreSQL only, with hand-readable SQL migrations No portability to other engines
Queue Durable jobs on Postgres, no external broker Not built for millions of jobs an hour
Coupling Modules integrate through events, never imports Cross-module flows are eventually consistent
Typing Models are Go structs, checked at compile time Schema changes need a deploy, not a click
Front end Server-rendered pages, progressive enhancement Less interactivity than a full SPA out of the box
Tenancy Schema-per-tenant, enforced by the kernel Very high tenant counts need sharding work
Licence Apache 2.0, one edition, no paid tier held back The project has to fund itself another way

The right-hand column is the honest half. If any of those costs is unacceptable for your business, Meru is the wrong tool and no amount of roadmap will change that.

Where this is going

Roadmap

Four phases. Each one has to be genuinely usable before the next one starts — no phase exists only to prepare for a later phase.

  1. Phase 1 — Foundation

    Current

    The kernel and the module contract. Registry, dependency resolution, migrations, identity and tenancy. The deliverable is a binary that can install and remove a trivial module without downtime.

    • Module registry and lifecycle hooks
    • Data layer and reversible migrations
    • Users, roles and record-level rules
    • Schema-per-tenant isolation

  2. Phase 2 — Core business

    Next

    The modules that make it an ERP rather than a framework: double-entry accounting, inventory with valuation, and the sales and purchase cycle that connects them.

    • Chart of accounts, journals, ledgers
    • Warehouses, stock moves, valuation
    • Quotations through to invoicing
    • REST and gRPC surface for all of it

  3. Phase 3 — Extended

    Later

    The functions that surround the core — customers, employees and production — each one a test of whether the contract is good enough for outside authors.

    • CRM pipelines and activity tracking
    • HR records, attendance and leave
    • Manufacturing BOMs and work orders
    • Localisation packs per country

  4. Phase 4 — Platform

    Later

    Turning Meru from a system you deploy into one other people build on.

    • Studio: models and views without Go
    • Marketplace for third-party modules
    • Reporting and query builder
    • Signed modules and version pinning

Frequently asked

No. Phase 1 is still in progress and there is no release to install. The design is public so that people who run ERPs can push back on it before the decisions are expensive to reverse.

Teams who run their own infrastructure, have engineers who can write a little Go, and want the system of record to be something they can read and operate themselves. If you want a hosted product with a sales engineer attached, this is not that.

Static binaries and a small runtime footprint remove most of the operational work we set out to avoid. Compile-time types catch a class of bug that matters more in accounting than in most software, and goroutines let one process handle concurrency that would otherwise need a worker pool.

For first-party modules, no — they are compiled in and enabled per tenant at runtime. For a module you wrote yourself, you rebuild the binary with it included. Loading arbitrary compiled plugins at runtime is deliberately out of scope for Phase 1.

PostgreSQL 14 or newer, and nothing else. The job queue, the event outbox and tenant isolation all sit on Postgres, so there is no separate broker or cache to operate.

Pages are rendered by Go templates and enhanced with a small amount of JavaScript. You can build a SPA against the REST or gRPC API if you want one, but nothing in the platform requires a front-end build step.

Not yet, and importers are not a Phase 1 or Phase 2 goal. Once the core modules settle, their schemas are plain Postgres tables, so an import is a normal ETL job rather than a special API.

Apache 2.0, with no separate enterprise edition planned. Modules published by third parties can carry whatever licence their authors choose.

At this stage, design feedback is worth more than code. If you have operated an ERP in production and know exactly where it hurt, open an issue and describe it — that is the input the module contract needs most.
